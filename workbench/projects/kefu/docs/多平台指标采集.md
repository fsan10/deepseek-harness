# 多平台接待量与店铺体验分采集

## 使用入口

- 接待量采集：`/reception/collection`。
- 店铺体验分采集：`/scores/collection`。
- 多平台采集设置、飞书配置：`/collection/settings`；店铺登录、启停和逐店采集范围：`/collection/settings/shops`。
- 抖音评价采集在 `/reviews/collection`；评论、接待量、体验分及异常配置统一在 `/collection/settings` 的顶部菜单中切换。旧 `/reviews/settings` 地址自动跳到评论配置。

正式启动沿用 `scripts/start-local.ps1`。打开采集或设置页面后会启动指标调度进程；定时计划默认关闭，执行期间保持网页服务运行。关闭浏览器页面不影响任务，退出网页服务会取消其所属采集进程，未完成任务可在下次启动后重试。

## 首次配置

1. 打开 Cloak Login，进入顶部「店铺配置」点击「同步店铺」。同步只读取账号配置，不启动店铺浏览器。
   每家店铺点击「配置」分别勾选评论、接待量和体验分。定时计划统一使用这里的范围，不再单独保存参与店铺清单。旧计划的选店范围首次升级时迁入对应店铺的采集配置，历史任务清单保留。
   「停用」表示后续不再采集该店铺，「启用」后按勾选范围恢复。MOCK吉饮咖啡专卖店及备注中的关店店铺默认停用，允许显式启用；重新同步保留人工选择，历史数据不变。账号被移除或平台信息不匹配时仍须先核对账号。
   店铺配置抽屉中的「自动检查登录状态」默认开启；启用中的店铺按「运行与环境」保存的间隔定时检查。可对天猫或任意店铺单独关闭，保存后不再进入后续定时检查；手动检查、登录和采集时自动恢复照常可用。同步店铺、批量设置采集范围、停用后重新启用均保留该选择。
2. 核对 profile 备注中的 `platform/company/shop`，以及精确的「入库店铺」映射。不按近似名称、大小写或后缀自动合并店铺。
3. 对需要采集的店铺点击「登录」。先进入店铺首页，复用 `mock_coffice` 的登录恢复模块；API 核对店铺身份通过后，按 profile 加密保存会话。
4. HTTP 检测到会话失效时自动调用同一登录功能，重新提取并加密保存 Cookie，再重试原采集。登录遇到验证码、滑块或二次验证时，群内通知并保留该 profile 等待处理；人工完成后自动继续，超过 5 分钟仍未完成才通知登录失败。权限、频率限制和店铺身份异常单独处理，不盲目重新登录。未排除人工异常的 profile 不会自动关闭；用户原已运行的浏览器也不会被关闭。
5. 在接待量或体验分采集页的「立即采集」面板选择平台，点击「采集店铺」可搜索、多选并确认店铺；默认使用当前平台的全部可采集店铺。接待量另选日期范围，体验分使用平台最新快照，然后开始采集。成功部分会保存检查点，重试只处理失败的店铺和日期。

采集页顶部展示本批进度、入库指标和异常店铺数；任务区展示逐店、逐日期的来源口径和结果说明。「最近采集任务」保留最近 20 次记录，支持分页和点击「详情」查看。任务进行中可取消，部分完成、失败或取消后可重试未完成部分。页面每 5 秒自动更新状态，平台、店铺和日期选择不会被轮询重置。

天猫仅使用 `TMALL-天猫-MOCK旗舰店`，小红书仅使用 `XHS-小红书-MOCK旗舰店`。抖音、京东、快手、拼多多按对应业务前缀发现。千川、财务专用天猫、推广专用小红书、巨量云图、直播、视频号均不接入。已关店或备注平台冲突的账号禁止登录和采集。同步中消失的 profile 会停止参与新任务，历史数据保留。

天猫 API 店铺名为 `MOCK旗舰店`，新数据使用该名称；原 `mock天猫旗舰店` 历史记录不改写。快手已确认 `MOCK禧饮咖啡专卖店` 与 API 的 `MOCK禧饮专卖店` 是同店别名，仅用于本项目身份核对，保留 profile 及备注。其他名称差异仍按精确名称核对；需要另一入库名称时在设置中明确保存映射。

## 统计口径与日期

| 平台 | 接待量来源口径 | 体验分 |
|---|---|---|
| 抖音 | 店铺接待会话量 `shop_serv_conv_cnt` | 总分、商品/物流/服务分、有效订单与动态分项 |
| 京东 | 接待量 `receiveNum` | 不采集 |
| 快手 | 人工会话量 `manualAskSessionCnt` | 不采集 |
| 天猫 | 生意参谋咨询人数 `cstUv1d` | 真实体验分、宝贝质量、物流速度、服务保障、有效订单与动态明细 |
| 拼多多 | 咨询人数(人) `consultUserCnt` | 消费者服务体验分、五个分项与同行排名区间 |
| 小红书 | 会话量 `caseCnt` | 不采集 |

接待量在分析中统一保存为 `接待量/运营/单`，来源名称保留在记录备注和任务明细。默认昨天，按北京时间解释，单次可选连续 31 天。平台历史可用范围不同：拼多多的逐日接口提供最近约一个月的数据；缺少请求日期时记录 `DATA_NOT_READY`，不回填 0。

体验分仅采集平台最新快照。平台业务日期可能比采集当天早一至数天，按 `done_date/readyDate/endDate` 保存；不把当前分数伪装成历史分数。采集时间另存于任务来源记录。抖音 V10 接口的百分制分数按原值保存，百分比转换保留分数与比例的区别；拼多多排名保留 10% 档位完整区间。

无值、日期不一致、重复日期、未知单位、缺少主指标或返回非 JSON 均不作为成功。平台明确表示暂无体验分时记录「平台暂无数据」。三类任务分别保存计划和进度，共用跨进程执行锁。到期或手动入队的任务不会抢占正在执行的任务；当前任务结束后，按「采集计划」表格的已保存顺序选择待执行任务，默认店铺体验分、评论、接待量。在计划表中拖动左侧手柄（也可聚焦手柄后按上下方向键），点击「保存计划」持久化顺序；刷新和服务重启后仍然保留。相同时间到点、或另一任务运行期间到点，都会等待依次执行。

## 登录与 HTTP 边界

业务模块为 `metric_collect.py`、`metric_http.py`、`metric_parsers.py`，不使用浏览器、CDP、DOM 或页面 fetch。只有 `metric_auth.py` 在用户点击登录或 HTTP 会话失效后自动恢复登录时连接浏览器，复用共享登录代码，并从独立 HTTP 身份接口确认店铺。

评论、接待量和体验分共用账号与登录状态，会话默认位于 `data/collection-auth/*.enc`，使用当前 Windows 用户 DPAPI、原子替换和会话代际校验。原 `review-auth`、`metric-auth` 目录中该账号最近保存的加密会话在首次读取时迁移到共用目录；旧目录配置仍可作为迁移来源。登录与报表使用相同浏览器互斥锁，纯 HTTP 采集不取得该锁。后台由一个账号轮询入口检查已保存会话，停用或风控后停止普通轮询；会话失效先尝试自动登录，明确登录失败或人工验证超时后停止反复重登，等待处理或重试未完成任务。

天猫 MTop 签名由当前加密会话在请求时生成，不保存、输出或复用旧动态签名。千牛和生意参谋通过 API 主账号归属核对；不同系统的子账号后缀大小写差异不改变店铺名称匹配规则。

## 飞书与人工处理

在采集设置中填写 App ID、App Secret、群 Chat ID，可选提醒人员 Open ID。自建应用需要消息发送权限、加入目标群并完成应用发布。保存配置不会发送测试消息；普通登录失效本身不发送人工接管提醒，先自动恢复；登录遇验证码、滑块或二次验证时即时提醒，等待超过 5 分钟后另发登录失败提醒。明确的自动登录失败、权限、身份、接口结构和采集异常仍保留独立原因。相同任务、店铺、错误类型合并提醒，保存发送结果和失败原因。

App Secret 和共享服务令牌只保存在 `data/collection-alerts.enc`，页面只返回是否配置，不回显密钥。更新时密钥留空表示保留；可以关闭提醒。未启用时记录「提醒未启用」，之后开启也不补发旧提醒。HTTP 200 不等于发送成功，必须收到飞书业务成功和消息 ID。

可选填写 `mock_coffice` 的人工处理服务地址及机器人令牌，手动或自动登录时向共享登录模块临时注入；不会写入 Windows 用户或系统环境变量。异常提醒配置由用户自行填写，交付不代填凭据、不发送真实飞书消息。

## 日志与异常

三个入口职责分开，底层共用 `collection_events` 一张表：服务日志保留服务心跳、登录检查结果与登录失效/检查异常/恢复记录；运行日志保留全部手动与定时任务、采集范围、各店铺结果、数量与失败原因，并支持按触发方式筛选；异常记录汇总两类来源，展示来源、最近发生时间、平台、店铺、关联任务、原因与处理状态，可跳回对应任务或服务日志。

同一店铺持续失效只保留一条待处理事件，后续失败任务合并关联；恢复有效时自动标记「已恢复」并保留历史，再次失效才产生新事件。飞书提醒发送记录通过 `collection_notifications.event_id` 挂在对应事件上，在异常记录里展开即可查看发送时间、结果与失败原因，不再单独维护一份发送记录列表；历史数据没有 `event_id` 时按店铺与事件存续时间兜底关联。

## CLI

使用本项目 Python；stdout 是统一 JSON 信封，登录日志不携带凭据。

```powershell
& .\.venv\Scripts\python.exe -m automation.commerce_cli platforms
& .\.venv\Scripts\python.exe -m automation.commerce_cli metrics profiles
& .\.venv\Scripts\python.exe -m automation.commerce_cli metrics auth login --profile <profile-id>
& .\.venv\Scripts\python.exe -m automation.commerce_cli metrics auth status --profile <profile-id>
& .\.venv\Scripts\python.exe -m automation.commerce_cli --platform pinduoduo reception fetch --profile <profile-id> --date 2026-10-21
& .\.venv\Scripts\python.exe -m automation.commerce_cli --platform tmall score fetch --profile <profile-id>
& .\.venv\Scripts\python.exe -m automation.commerce_cli --platform jd reception collect --profile <profile-id> --from 2026-10-20 --to 2026-10-21
& .\.venv\Scripts\python.exe -m automation.commerce_cli reception status
& .\.venv\Scripts\python.exe -m automation.commerce_cli reception retry --run-id <run-id>
```

`fetch` 只返回 API 数据，不导入指标。`collect` 加入队列，需要网页服务及其 worker 运行。采集器向本机 `/api/import` 先校验后正式导入，使用 `.env.local` 中的 `IMPORT_API_KEY`；独立运行时可设置 `KEFU_IMPORT_BASE_URL`，网页 worker 自动使用当前服务端口。密钥不得放入命令行。

指标业务表沿用 `shops/metrics/daily_records`；新增 `metric_*` 只保存账号、认证状态、设置、任务和来源审计。唯一约束防止重复任务和重复检查点，导入接口按日期、精确店铺和指标幂等更新。原影刀脚本保留用于历史兼容，新采集流程不调用 DOM 解析脚本。
