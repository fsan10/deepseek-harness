# 02 · 信息架构与页面职责

## 1. 四条设计原则

1. **一页一问**：页面标题就是一个问题；页面首屏必须能回答它。
2. **一页一主操作**：主操作只有一个，放在顶栏右侧或首屏操作区；其余动作降级为文字链或行内操作。
3. **外壳复用、内容独立**：侧栏、顶栏、筛选条、面板、表格、状态、日期全部来自共享层；页面只负责组合与业务文案。
4. **URL 即状态**：筛选、日期、分页写入查询参数；刷新、分享、后退都可复现。

## 2. 新信息架构

```
客服数据台
├─ 分析
│  ├─ 经营总览        /overview
│  ├─ 接待量分析      /reception
│  ├─ 店铺体验分      /scores
│  └─ 差评分析        /reviews
├─ 运营
│  ├─ 评价采集        /reviews/collection
│  └─ 数据维护        /data
└─ 配置
   ├─ 采集设置        /reviews/settings
   └─ 数据接入        /data/import
```

分组依据是**使用频率与风险**，不是数据表：
- 分析：每天看，只读，错了影响判断。
- 运营：需要动手，写数据或启动任务，错了影响生产。
- 配置：低频，改一次长期生效，需要更明确的确认。

## 3. 八个页面的职责边界

| # | 页面 | 唯一职责 | 输入 | 输出 | 主操作 | 明确不负责 |
| --- | --- | --- | --- | --- | --- | --- |
| 01 | 经营总览 | 用一屏回答「今天最该关注什么」 | 数据日（系统推导） | 摘要、4 个 KPI、7 天趋势、平台占比、异常、体验分排行 | 导出摘要 | 不编辑、不采集、不做多店对比、不做全量明细 |
| 02 | 接待量分析 | 判断涨跌与贡献结构 | 平台、日期范围 | 4 个 KPI、30 天趋势、平台合计、店铺明细 | 导出明细 | 不看体验分细项、不写数据 |
| 03 | 店铺体验分 | 定位单店短板 | 店铺、日期范围 | 5 张评分卡、其他指标、30 天趋势、全店对比 | 切换店铺 | 不做跨店编辑、不解释平台规则 |
| 04 | 差评分析 | 看清抱怨主题与集中商品 | 店铺、评价日期、等级、搜索 | 4 个 KPI、关键词、明细、商品 TOP | 导出 Excel | 不启动采集、不改定时、不重试任务 |
| 05 | 评价采集 | 推进本轮任务并处理卡点 | 店铺范围、采集日期 | 进度、店铺状态、最近任务、运行环境 | 开始采集 | 不展示评价明细（跳转差评分析）、不改定时规则 |
| 06 | 数据维护 | 找到并修正一条记录 | 类型、平台、店铺、日期、关键词、分页 | 记录列表、编辑弹窗、删除确认 | 新增记录 | 不解释接入协议（跳数据接入）、不做批量导入 |
| 07 | 采集设置 | 设定采集规则与数据源 | 频率、回溯天数、执行时刻、店铺清单 | 下次执行时间、服务状态、店铺清单 | 保存配置 | 不立即执行采集（回评价采集） |
| 08 | 数据接入 | 说明外部程序如何写入 | 无（读文档） | 端点、鉴权、字段表、失败规则、模板 | 下载 CSV 模板 | 不浏览业务数据（回数据维护） |

### 三处关键拆分

**A. 差评页一拆三**

| 原能力 | 去向 | 理由 |
| --- | --- | --- |
| KPI、关键词、明细、商品排行、导出 | 差评分析 `/reviews` | 只读分析，高频，需要稳定筛选 |
| 立即采集、同步店铺、任务进度、重试 | 评价采集 `/reviews/collection` | 有副作用，需要明确的进行中/失败/待人工状态 |
| 定时开关、频率、回溯、执行时刻 | 采集设置 `/reviews/settings` | 低频配置，改错会影响后续所有任务 |

**B. 数据维护一拆二**

| 原能力 | 去向 | 理由 |
| --- | --- | --- |
| 类型切换、筛选、列表、编辑、删除、新增 | 数据维护 `/data` | 面向「修一条数据」 |
| 批量导入弹窗（端点、鉴权、批量上限） | 数据接入 `/data/import` | 面向「接一套自动化」，需要完整字段与失败规则 |

**C. 总览不再承担导航职责**

原页面底部的 CTA 条（「查看接待明细」「查看店铺评分」「进入数据管理」）是导航缺失的补丁。新方案由侧栏承担导航，总览只保留**有语义的下钻**：摘要 → 接待量、异常 → 体验分、体验分排行 → 体验分、采集状态 → 评价采集。

## 4. 共享层

| 层级 | 内容 | 复用方式 |
| --- | --- | --- |
| L0 Token | 颜色、字号、间距、圆角、阴影 | CSS 变量 / Tailwind theme |
| L1 原子 | Button、Select、Input、SearchField、Chip、Tooltip | 组件 props |
| L2 复合 | KpiCard、PanelHeader、FilterBar、DataTable、Pagination、EmptyState、ErrorState、Skeleton、Toast | 组合使用 |
| L3 领域 | DateField、DateRangeField、DataDateTag、TimeField、StatusChip、PlatformTag、MetricValue | 统一口径 |
| L4 区块 | 趋势面板、排行面板、异常列表、任务进度 | 页面内组合 |
| L5 页面 | 8 个路由 | 只取数 + 组合 + 文案 |

**壳层规格**：侧栏 232px（≤1180px 收为 210px，≤860px 变抽屉）；顶栏 62px；内容区内边距 24/20；最大内容宽 1440；卡片间距 14；卡片圆角 14；控件高 34–36。

## 5. 数据契约（建议）

现状是 `GET /api/dashboard?view=...` 一个端点返回四种 payload。建议按页面拆端点，每个端点只返回该页需要的字段：

| 页面 | 建议端点 | 主要参数 |
| --- | --- | --- |
| 总览 | `GET /api/overview` | `date?`（缺省取最新数据日） |
| 接待量 | `GET /api/reception` | `from,to,platform` |
| 体验分 | `GET /api/scores` | `shopId,from,to` |
| 差评分析 | `GET /api/reviews` | `from,to,shop,level,field,query,page` |
| 评价采集 | `GET /api/reviews/runs`、`POST /api/reviews/collect` | 任务与重试 |
| 采集设置 | `GET/PUT /api/reviews/settings`、`GET/POST /api/reviews/profiles` | 规则与店铺 |
| 数据维护 | `GET /api/records`、`POST/PUT/DELETE /api/records` | `type,platform,shopId,from,to,query,page` |
| 数据接入 | 静态文档 + `GET /api/import/template` | 模板下载 |

**统一响应外壳**（建议）：

```ts
type PagePayload<T> = {
  data: T;
  meta: {
    date: string | null;      // 本页口径的数据日
    updatedAt: string;        // ISO，北京时间展示
    empty?: "no-data" | "no-match";
  };
};
```

原则：
- 不再出现 `view` 参数；一个端点只服务一个页面。
- `rows`、`trend`、`latestDate` 这类泛化字段名不再跨页复用；改为 `shopRows`、`receptionTrend`、`metricDate` 等具名字段。
- 指标格式化、目标判断、5 分制换算只在服务端做一次，客户端只负责展示。

## 6. URL 状态约定

| 页面 | 示例 |
| --- | --- |
| 接待量 | `/reception?from=2026-09-22&to=2026-10-21&platform=抖音` |
| 体验分 | `/scores?shopId=12&from=2026-09-22&to=2026-10-21` |
| 差评分析 | `/reviews?from=2026-10-20&to=2026-10-21&level=差评&field=keyword&q=口感&page=2` |
| 数据维护 | `/data?type=reception&platform=抖音&shopId=12&from=2026-10-01&to=2026-10-21&page=1` |

约定：
- 日期一律 `YYYY-MM-DD`；空值不写入 URL。
- 分页从 1 开始；切换筛选时重置为 1。
- 下钻时携带来源标识（`?from=overview`），返回时回到来源页并保留筛选。

## 7. 迁移映射

| 现状 | 目标 | 处理方式 |
| --- | --- | --- |
| `Dashboard.tsx` 的 `view` 状态 | 8 个路由 | 每个条件块抽成 `app/(console)/<route>/page.tsx` |
| `overview` 分支（`:484`） | `/overview` | 去掉 CTA 条，改为语义化下钻 |
| `reception` 分支（`:501`） | `/reception` | 筛选与表格抽组件，补分页 |
| `store-score` 分支（`:514`） | `/scores` | 评分卡改用 KpiCard；对比区保留 |
| `data-management` 分支（`:525`） | `/data` | 移除导入弹窗，链接到 `/data/import` |
| `ReviewAnalytics` 分析段 | `/reviews` | 只保留 KPI/筛选/关键词/明细/商品排行/导出 |
| `ReviewAnalytics` 采集配置段 | `/reviews/collection` + `/reviews/settings` | 立即采集与任务进度 → collection；定时规则 → settings |
| `exportCsv()`（`:402`） | 各页 ExportAction | 每个页面明确导出对象与范围，文案写清 |
| `DateRangePicker`（`:195`） | `DateRangeField` | 保留双月日历，补齐键盘与预设 |
| `FancySelect`（`:128`） | `Select` | 统一键盘与空态 |
| `Panel`（`:320`） | `DataPanel` + `PanelHeader` | 统一 h2/副标题/动作位 |

## 8. 页面验收清单

- [ ] 8 个路由可独立打开，刷新后筛选不变。
- [ ] 每页只有一个主按钮；其余动作不超过 2 个次级入口。
- [ ] 每页首屏能看到该页问题的答案，不需要滚动。
- [ ] 所有表格共用同一套表头、行高、分页、空态。
- [ ] 所有日期使用 L3 组件，无原生日期输入。
- [ ] 所有错误都有「重试」，所有空态都有「下一步」。
- [ ] 导出按钮的文案能说明导出范围（当前筛选 / 全部 / 当前页）。
