# 导入、来源采信和重试评审加固

## 设计与修补范围

根据当前调用链核对评审报告后，采用“收口新增旁路、保留历史、冻结计算、单独诊断”的方案。
不修改 ODS 原始记录，不迁移或删除现有人工登记，不改变经营金额、分类和退款公式，不扩大自动发布月份。

| 原问题 | 可能后果 | 实施方式 |
|---|---|---|
| 人工 manifest 可新增宽范围登记 | 只有数天明细却声明整段范围，未明确采信日期的旧来源可能被遮住，造成漏算 | 新增登记仅允许内部核验的自动化回执；旧人工 CLI 拒绝；对账维护脚本也不再登记新来源 |
| 回执核验仅在调用方 | 其他调用者伪造 evidence_type 可能绕过来源证据核查 | 在 register_source 写入边界重新核对回执与文件、店铺、批次、请求区间 |
| 全局最大批次不能解释相关快照变化 | 资金已经入库却继续报告缺失，或其他店铺上传造成错误“过时”提示 | 按运行相关报表、店铺、月份检查；包含后来完成的排除批次和无新 ODS 的采信变化 |
| 钱包对账依赖已发布资金 DWD | 跨月到账尚未发布时找不到；旧快照可能混入后来发布的资金 | 使用冻结的资金来源，沿用同一七字段事件身份和金额符号，不发布依赖月份 |
| 交易最大日被误解为完整资金覆盖 | 早期没有上传或中间有缺口时误报真实缺失，或误当正常待到账而通过 | 完整覆盖只来自已批准完整导出的日期；交易边界单独显示；历史未覆盖、未知、真实缺失全部阻断 |
| 日期前缀校验缺失 | 1999、2100 等编号被当作预计日期，误判缺失或待到账 | 前八位严格匹配 20 加六位 ASCII 数字，并校验合法日期；失败沿用原结算日加一天 |
| 对账输出把单据组数叫批次 | 用户把多个物理批次误解成一批 | 增加 group_count、真实 source_batch_count 和各批次日期清单；旧字段只作弃用别名 |
| 原快照重放可能被误当只读诊断 | 用户不经意用旧数据替换当前指标 | 页面仅提供最新数据重跑；高级 API/CLI 重放须明确确认写回，并写入审计信息 |
| 店铺参数和重跑范围不够明确 | 旧客户端上传失败难以识别；误以为重试会补算其他月份 | HTTP 400 附 SHOP_CODE_REQUIRED，保留数字 code；页面显示原范围，不自动扩展 |

## 具体实现

- `etl/common/settlement_sources.py`：历史相同登记可继续幂等核验；新人工登记拒绝。
  新回执在函数内部核对 artifact、SHA256、标准店铺、请求日期、批次绑定和小红书同工作簿配套表。
  保留历史分片组，新增回执不接受手工指定分片组。
- `etl/platform_finance/reconcile_settlement.py`：删除人工登记调用；继续核对旧登记。
  新流程已采信的抖音文件按当前有效源的全业务字段多重集核验，再刷新既有指标。
  其他平台在具备同等人工采信保护前，不新增人工范围替换。
- `etl/common/source_coverage.py`、`apps/file_ingest/refresh_scope.py`：冻结完整覆盖业务日、连续区间及检查日期。
  批次上限、冻结时排除批次和采信上限共同约束证据；空文件补缺保留旧明细的日不能充当完整证明。
- `etl/jd/wallet_reconciliation.py`：严格日期前缀；分开输出物理批次与单据组；交易边界与完整覆盖分开。
  钱包来源直接受同一冻结运行时约束；跨月只读取依赖，不扩大 DWD/DWS/ADS 发布范围。
  `uncovered_count`、`coverage_unknown_count`、`missing_count`、`amount_mismatch_count` 均阻断事务。
  预计日当日及未来可暂记预计待到账；新快照保存检查日期以支持一致复现。
- `apps/file_ingest/source_diagnostics.py`、`service.py`：执行前观察，失败后复核，并将结构化结果写入原有 result_metrics。
  详情接口单独返回当前观察，注明观察时间；提示不参与金额计算、不更新快照、不扩大范围。
- `apps/file_ingest/errors.py`、`module.py`、`cli.py`、`static/app.js`：业务错误码、重放确认、最新重跑按钮、范围与快照差异提示。

## 使用变化

1. 人工采信使用网页或 `apps.file_ingest.cli`；重复文件可复用原批次，无需重传。
2. 原 `settlement_sources --manifest` 只接受带真实 artifact 的自动化回执。新的人工作业不能以普通说明字典直接写 registry。
3. `reconcile_settlement --apply` 是已批准来源的核对/刷新工具，不是授权覆盖的入口。
4. 原快照正式重放必须显式发送 `confirm_replay_publish: true`；CLI 对应 `--confirm-replay-publish`，缺少时在登录前拒绝。
   正在排队或执行的关联运行只允许相同快照方式复用，避免把最新数据重跑与原快照重放互相混用。
5. 新增 HTTP 错误的顶层 `code` 仍是 400，机器可识别原因位于 `data.details.error_code`。
6. 新字段使用原有 JSON 上下文与结果字段，无建表迁移。后端和独立 Worker 重启后生效，成功业务文件不必重传。
