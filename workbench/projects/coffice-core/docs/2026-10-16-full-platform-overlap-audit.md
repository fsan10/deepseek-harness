## 0. 总体结论

**是，当前已不会出现数据重叠。** 结算侧与混合侧的全部 14 项关键检查均通过：

- 结算侧：全平台"同一天存在多个有效来源" = **0 例**；所有历史重叠（9/22、9/23、9/27 的日报与月报交汇）均被正确去重并有明确覆盖记录。

### 2.5 映射层"准入交叉"检查（防双计的结构性关口）

把两条准入条件（费用 DWS 的 `include_in_platform_expense=TRUE` 与 scene 兜底的 `canonical='excluded'/NULL`）做交叉矩阵：

```
inc=True 且 canonical 为 NULL/excluded 的映射 → 0 行（不存在"两侧同时捞"的组合）
inc=False 且 canonical 为 expense 的映射      → 0 行（不存在"两侧都不捞"的漏行组合）
```

> 其余 `inc=False 且 canonical=income` 的行（订单实付、各类补贴、退款等约 40 条）由各平台收入 DWS 的组件逻辑处理，不漏不重。

### 2.6 跨来源防重（结算 vs 资金）

- 快手收入链路内置**跨来源查重**：资金的"资金扣减 + 快手小店退款"行，若结算单已有同订单退款（`order_refund_amount > 0`），该资金行不再计入收入 —— 从机制上避免"同一退款在结算、资金两处各扣一次"。
- 资金勾稽类（货款结算、冻结/解冻、扣减前临时解冻）全部归 `settlement_reconciliation`，不进入收支。

## 3. 机制可维持性

- 每次 ETL 刷新前都会先执行来源校验（`prepare_settlement_sources` / `prepare_finance_sources`）：范围不明、来源交叉、导入不完整等任何一项不通过，**整批刷新会中止而非静默出错**。
- 覆盖登记支持自动回执（`automation_receipt`）与人工确认（`user_confirmed`）两种证据来源；新批次会自动登记或阻塞。
- 单元测试覆盖：`etl/common/tests/test_settlement_sources.py`（覆盖选择/冲突/分片）、`test_finance_sources.py`；文档：`docs/settlement-source-reconciliation.md`、`docs/operating-finance-source-reconciliation.md`。

## 5. 两个观察项（不影响当前数据，建议后续处理）

1. **快手 3 条映射的"角色"与实际行为不一致**（建议修正为一致）：
   `ks_fund_0d0fdcce`（MCN 机构返还）、`ks_fund_e1d58ce7`（超售后期退款扣减）、`ks_fund_e6814c42`（退货包运费垫资追款）的 `source_role` 目前是 `RECONCILIATION`（"仅核对"），但实际金额经兜底分别计入了费用/收入。
   金额的业务含义正确，但建议按实际行为把 role 改为 `EXPENSE_OFFSET` / `REFUND_SUPPLEMENT`，否则未来若增加"role 与计入行为一致性"校验时会报错，也会让审计人员误读。

2. **"精确匹配"边界脆弱性（防回归提醒）**：
   快手收入 DWS 对资金退款用 `source_description = '快手小店退款'` 的**精确匹配**，"快手小店退款-超售后期"依赖兜底链路补入（金额 −198.00）。当前无双计，但如果有人把该匹配放宽为 `LIKE '快手小店退款%'`，这 198 元会**真正双计**。
   建议：为这条链路补一个互斥断言或测试用例（例如断言"scene 收入端 '快手小店退款-超售后期' 只出现一次"），把边界固化住。小红书链路同型（费用 DWS 里的小额收款与收入归位的关系），一并纳入测试。
