# 2026-10-20 导入补缺与重试修复说明

## 与参考方案的取舍

保留 DeepSeek 方案中的 ODS 不变、范围声明、影响预检、人工裁决、刷新快照和统一入口思路。原方案文件保留，具体实施采用 [统一契约](ingest-coverage-contract.md)。

修正以下判断：

1. 区间内每天都有明细不是完整性的必要条件；零交易日合法。真正需要拦截的是不经确认用空日删除旧来源。
2. 金额和行数相同不足以证明数据重复；本实现比较全部源业务字段及重复行数量。
3. 对京东这次事故，原范围仍是同一家店的十月，本身没有问题；重试要更新来源快照并重新加工相关节点，不必去掉导入关联或改为全量。
4. 京东失败节点本身包含 DWD 重建，“上游没有级联”不是这次失败的另一项已证实原因。重新执行整条相关链路是通用修复策略。
5. 不按证据类型或整月/单日直接决定财务真值，明确的人工采信决定优先，其余冲突保持可见。

## 一、补缺与日期重叠

旧机制只能在覆盖范围已登记时选择宽范围，人工上传没有声明与预检路径，因此累计文件与旧日文件同时有效时停止刷新。

修复后的流程：

- 自动化日历继续按业务日期计算缺口，不能用文件名或执行日代替。
- 用户不清楚缺哪天时可以上传整段导出，不要求先人工找出缺失日期。
- 逐日相同内容保留既有来源；没有来源的日期从新文件补齐；内容差异展示后由人工处理。
- 有完整查询声明时，把零交易日也纳入预检。未知范围不推断为空日。
- 来源采信记录按平台、标准店铺、独立报表和业务日追加，区间交叉按日裁决，范围外来源保留。

边界：跨月会生成多个受影响月份；新文件少了旧账户时拒绝非空范围替换；同一会话的重叠文件/不明确分片拒绝提交。原 ODS 行、原批次及旧报错保留。

用户提示分开说明：“文件已入库”“已补齐/采信哪些日期”“指标是否刷新成功”。

## 二、整段版本替换及重复文件

文件是否需要再次入库和是否重新采信是两个独立问题。新增 `replace_range` 和“复用这些文件并重新核对”入口：

1. 相同 SHA256 使用原成功批次；不重复写 ODS。
2. 明确实际查询范围，确认完整导出并填写替换原因。
3. 预览逐日差异、旧来源批次、行数及原始金额。日期范围内新空旧有需逐日确认。
4. 提交匹配预检的令牌，后端再次校验当前来源和文件。
5. 写入新的采信版本并按该范围排队增量刷新；旧文件即使导入时间更早，也能因为新的人工决定成为当前采信来源。

默认自动化不得覆盖人工采信的差异数据；宽范围文件也不会无条件胜过窄范围。相关日期在预检后变化时令牌失效；无关店铺变化不使其失效。所有入口遵守同一规则。

边界：已确认零交易日受到保护，后续自动化新记录不能把它当作缺口自动覆盖。复用草稿取消或删除不会删除原始文件。

## 三、京东资金就绪后仍重试失败

这次失败会话 `9750b31c` 的冻结来源只到批次 776，909.72 元资金流水位于后来导入的批次 777。旧实现重试保留原 `refresh_context`，所以再次执行仍读不到 777。

修复：

- 普通“重试”使用 `latest`，创建新关联运行，更新成功批次上限、排除批次和采信版本。
- 原店铺和业务月份保留，整条相关上下游重新排队，旧运行和报错不被改写。
- 执行中使用相同冻结来源，运行途中不混入新的批次。
- 京东对账按受影响范围内全部商户结算组及标准店铺核对，取消“只看最后导入的一份文件”。
- 对账按店铺隔离，不能用另一家店相同商户单号的资金来匹配。
- 错误信息包含来源上限及具体异常；预计未到账、缺少匹配和金额不一致分别统计。资金最大日期不能单独证明中间日期完整。

对现有数据库只读核验：京东十月当前涉及的 17 个商户结算组全部匹配，结算与资金各合计 8,266.39 元，缺失和金额差异均为 0。此核验没有重跑 ETL。

## 四、三个上传入口

| 入口 | 业务身份 | 日期和店铺输入 | 反馈与异常 |
|---|---|---|---|
| 网页人工 | 已登录用户、CSRF、上传权限 | 用户核对的 DIM 店铺与实际查询范围 | 逐日预览；有冲突禁用确认；可保留草稿、重新预检或复用旧文件 |
| 自动化 API | `api`/历史 `robot`；有效 Bearer | 标准店铺、报表、文件幂等键；可信回执绑定 SHA256 和真实请求范围 | 默认补缺；差异停止等待人工；分开查询 ODS、采信和 ETL 状态 |
| 终端 API | `manual`；用户登录会话 | manifest 显式提供标准店铺、报表和覆盖声明 | JSON 输出与退出码；分步预检/确认；可以按 run_id 续办 |

统一校验：文件格式/必需字段、SHA256、DIM、幂等参数、逐日多重集合、范围外记录、空日确认、账户完整性、来源并发变化及原始 ODS 完整性。

总控终端默认的 `--trigger-type manual` 使用用户登录，定时任务 `--trigger-type schedule` 使用自动化 Token；已同步修改原有归档上传器，显式传标准店铺、报表和查询声明，避免新契约只在新增 CLI 中生效。

鉴权补充修复：网关不再因任意 Bearer 字符串而绕过用户认证；有效自动化 Token 也不能通过把 `source` 写成 `manual` 来执行人工范围替换。凭据从未提交的 `.env`、交互输入或部署 Secret 获取。
