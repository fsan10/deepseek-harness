# 报表来源与导入修复

ODS继续保留全部原始批次，指标DWD直接从ODS来源视图选择有效版本。来源视图不含金额、订单状态或售后状态筛选，不复用任何指标表。

## 来源规则

- 订单按平台、标准店铺和主订单选择最新整单快照。标准文件名的报表日期优先，同报表日期按采集时间选择；旧报表重新上传不会覆盖较新的报表日期。同一提交的同日期分片共同参与整单快照。
- 有子订单的平台保留子订单业务键，其余平台由订单号、商品规格字段及同商品行序号构造明细键。金额、状态及ODS主键不参与业务身份。
- 拼多多结算只用源文件表头声明且经过明细校验的完整查询范围判断来源覆盖。完整月报覆盖旧日报，同范围的后续提交覆盖旧提交，同次提交的同范围分片保留。单个文件内相同订单号、金额和时间的流水全部保留。
- 不完整或无法识别的查询范围不授权覆盖整日。已有批次仅在源文件可访问且SHA256与导入记录一致时补登记范围，原始ODS明细不变。
- 每次刷新先核验全部历史来源批次的导入状态及DIM映射，历史未映射批次也会阻止刷新。

## 费用与身份

拼多多费用候选使用与DWD一致的“账务类型 + 业务描述”，已有扣款分类不会屏蔽新增描述。新增费用的一级分类仍由财务确认。用户于2026-10-12确认“扣款 + 0040006|售后费用-缺货”归入“售后赔付”并计入平台费用；正式映射沿用拼多多既有分类编码`after_sale_compensation`。

快手源商家ID对比DIM的`account_id`，内部标准`shop_code`保持不变，错误账号仍会阻止刷新。

京东结算时间缺失时使用账单日期零点；业务日期仍取账单日期，资金单仍取入账时间。资金费用名称与后台候选统一为交易类型，原始备注保留供已配置的细分规则匹配。

## 验证与升级

新增数据库回归测试位于`etl/common/tests/test_report_sources.py`，必须显式指定隔离测试库`REPORT_SOURCE_TEST_DB`，禁止对业务库运行。测试涵盖七平台版本选择、旧月报重新导入、分片、跨店同号、历史映射失败、结算合法重复及错误快手账号。

真实文件验收覆盖58个文件、59个ODS批次、178450行；通过HTTP登录、上传、提交和实际Loader验证，并验证重复上传幂等、日期越界时整体回滚。保留历史来源后，29项正式调度链路通过校验。拼多多新增费用的一级分类在隔离库使用临时测试配置，正式分类须另行确认。

最终执行128项回归检查，127项通过，1项因外部样本文件不可用跳过。另核对七平台共35条DWD来源样本、43条京东日期回退、拼多多跨月状态更新及快手账号身份。正式库31张ODS明细表的534201条原始记录在修复前后逐行摘要一致。

正式修复首次运行中26项任务成功；拼多多主营财务因缺货费用尚未确定一级分类而失败，其主营收入共享汇总及平台银行汇总两个依赖任务跳过。2026-10-12按用户确认写入正式费用映射，创建费用映射触发的增量范围刷新运行`2abca1c6-435f-4508-b98a-2910213208de`，上述三个节点全部成功，刷新水位同步更新。首次运行的失败、跳过记录保留为历史审计记录。

缺货费用的有效结算来源为两笔，每笔5.00元，DWD、DWS、费用ADS及平台银行汇总均核对为售后赔付10.00元。ODS仍保留三个原始来源记录，完整月报覆盖旧日报的规则只影响参与计算的来源。此次分类刷新前后30张`ods_*_raw`明细表的534201条记录逐行摘要一致；辅助Worker已停止，临时核验脚本已清除。原9月ODS无需重新导入。

Web应用迁移新增434、435。现有服务需重启以载入新的费用候选查询；单独运行ETL也会准备所需来源视图，拼多多Loader可以登记查询范围。抖音既有手机号类型迁移增加重复执行检查，避免服务重启后因视图依赖报错。
