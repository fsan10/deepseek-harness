# 平台收支配置与报表任务加载性能分析及修复

验证日期：2026-10-19，Asia/Shanghai。

## 结论与测量范围

两个页面的等待主要来自应用读取路径中的重复工作。数据库连接本身约 27～35 毫秒，但报表页面一次请求会连续建立 65 次连接；收支配置则在筛选前扫描全部平台，并对大量重复场景反复执行数据库清洗函数。日历另有明显的重复数据传输。

使用当前 PostgreSQL 和真实归档目录，先保留原实现基线，再运行修复后的相同读取逻辑。浏览器验收使用临时本机 HTTP 服务和真实页面脚本，目标接口调用真实服务及数据库；登录、权限及不相关的初始化接口使用测试替身。因此以下耗时不包含正式服务的 IAM 鉴权和用户网络条件，也没有替换当前正在运行的正式后端。

本次重现了约 2～3 秒的等待，没有重现超过 10 秒的单次等待。采样时数据库没有发现其他活动查询或锁等待，不能据此把用户遇到的那一次超过 10 秒直接归因于数据库锁。已经确认的逐日志连接、重复计算和大响应会放大网络、连接延迟及历史数据增长的影响。

## 实测结果

接口处理耗时包括连接、业务读取及 JSON 序列化；修复后的重复查询取三次中位数。修复前为基线采样值。

| 操作 | 修复前 | 修复后 | 变化 |
| --- | ---: | ---: | ---: |
| 平台收支配置，全平台 | 1.589 秒 | 0.361 秒 | 减少约 77% |
| 报表任务，列表 | 2.518 秒 | 0.239 秒 | 减少约 90% |
| 报表任务，日历 | 2.736 秒 | 0.364 秒 | 减少约 87% |
| 已同步历史日志检查 | 2.163 秒 | 0.086 秒 | 65 次连接降为 1 次 |

指定拼多多并搜索“扣款”的服务读取由约 1.55 秒降至约 0.09 秒。

浏览器从打开页面或点击切换到目标内容出现：收支配置首次显示 1.931 → 0.955 秒，报表列表首次显示 2.985 → 0.367 秒，日历首次显示 2.919 → 0.868 秒。修复后重复点击查询的三次中位数分别为 0.399、0.290、0.421 秒。首次进入还包含静态资源及页面初始化，不能与接口处理时间混用。

日历响应由 **4,277,456 字节降为 548,767 字节，减少约 87.2%**。

## 平台收支配置的原因与修复

读取入口是 `apps/file_ingest/service.py` 的 `list_fee_mappings` 和 `_fee_candidates`。

1. 原实现先读取全部平台配置、扫描七个平台 ODS 候选，再在 Python 中应用平台筛选。即使只查拼多多，也要等待抖音、天猫等来源完成。
2. 原查询的 `DISTINCT` 位于场景清洗表达式外层，PostgreSQL 需要先对重复明细执行 `dim.normalize_platform_scene`，再对结果去重。该函数会读取清洗规则并执行正则。基线中抖音、拼多多、天猫三段查询合计约 1.35 秒。
3. 天猫候选还有较长的 CASE/正则表达式；原过滤条件可被优化器下推，使同一场景表达式在筛选和投影中重复计算。执行计划显示两张天猫资金来源合计约 38,480 行，去重后只有 49 个原始候选组合。

修复方式：平台条件先传入配置查询和 ODS 来源选择；使用请求内 `WITH ... AS MATERIALIZED` 先按来源、业务类型、原始描述和场景去重，再过滤空场景并执行原数据库清洗函数。这是 SQL 执行顺序调整，不是新增物化视图或持久缓存。正则规则仍由 PostgreSQL 解释，新来源和规则变更仍在下一次查询中实时读取。

`apps/file_ingest/static/app.js` 同时补充加载提示、请求取消和请求序号校验。即使旧响应晚于新响应到达，也不能覆盖新筛选结果。经营归属、分类、未映射规则及保存行为保持原有语义。

## 报表列表、日历的原因与修复

读取入口是 `apps/automation_center/report_center.py` 的 `report_day`、`report_calendar`、`sync_report_journals` 和 `_report_evidence`。

### 历史日志形成逐条连接

归档日志目录有 66 个 JSON 文件，其中 1 个是清单，65 个是执行日志。原实现每次打开或查询页面，都会对每份日志单独连接数据库、获取事务级 advisory lock、读取已导入事件数；即使全部日志都已同步，也执行 65 个事务和 130 条查询。单次建立连接约 30 毫秒，累积就是秒级等待。

现在先读取日志事件数，通过一次数据库查询批量获取全部日志的导入偏移。已经同步的日志直接跳过。只有存在新增事件的日志才进入原有加锁事务；获取锁后再次检查偏移，防止 Web、Worker、Scheduler 并发重复导入。进程已退出但日志没有正常结束事件的判断仍然每次执行，不依赖文件修改时间缓存。

### 列表重复读取证据

原列表分别读取当天和最近七天证据，当天数据、文件状态和部分 SQL 被读取两次，且查询了列表并不使用的执行历史。

现在一次读取最近七天，复用于当天状态和最近七天完成数；列表及补跑预览跳过不需要的执行历史查询。按“Profile + 报表”和“Profile + 模块”建立请求内索引，避免每个日期、每份报表都遍历全量证据。归档根路径只解析一次，同一路径的文件检查在本次请求内复用；下一次请求仍检查实际文件，删除文件后仍会显示缺失。

### 日历响应过大

原月视图返回每天的完整明细 `items`、分组后的同一批报表、归档回执、重复店铺映射信息及执行快照，而页面格子、缺口明细和补跑选择只使用其中少量字段。

前端现在请求 `compact=1`，服务端只返回日历所需的汇总、店铺/报表身份、下载状态、上传状态和相关运行标识。未携带该参数的接口仍返回完整数据，保留原审计与执行历史语义。列表和日历响应一并提供筛选所需的公司/平台清单，首次进入不再串行请求额外的完整目标清单。前端保留查询序号保护并取消过期请求。

## 生效与范围

本次调整应用读取逻辑和页面请求方式，不需要执行数据库结构迁移或重算财务指标。ODS 原始数据、财务金额、分类和来源防重规则没有变更。

按项目要求，测试临时服务和浏览器均已关闭，数据库测试数据均通过事务回滚清除；未创建正式 IAM 登录会话。当前用户原有服务未替换。需要用户重新启动现有后端、AutomationWorker 和 AutomationScheduler，并刷新页面，才能让现有服务加载本次代码。

本次测试数据量是当前库的快照；未把结果外推为更大数据量下的固定响应时间。读取仍然实时访问 ODS 和归档文件，后续若来源继续显著增长，应以新的执行计划和请求分段计时决定下一步优化。
