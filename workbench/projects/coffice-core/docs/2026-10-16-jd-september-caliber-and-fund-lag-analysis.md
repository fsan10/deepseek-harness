## 0. 结论速览

1. **"T+1"在京东链路里只存在一处**：经营 ETL（`etl/jd/run_jd_main_business_finance_etl.py`）的
   **"结算→钱包跨日对账"闸门**。结算口径与经营口径的**金额计算本身不按 T+1 对齐**——
   两个来源各用各自日期（结算=`账单日期`，资金=`入账时间`），没有跨源日期平移，所以"差 1 天"不影响月度金额。
2. **事实核对：您的记忆是对的。** 正常期账单日 T → 钱包到账 T+1（9/1~9/29 共 29 个批次、合计
   16,167.79 全部逐笔精确匹配）；而 **9/30 的账单（净额 828.01）到 10/8 才到账——正好差 8 天**
   （国庆 10/1~10/7 不打款，9/30~10/7 共 8 个批次的结算款全部挤到 10/8 到账）。
3. **但问题不在"按 T+1 算"，而在"8 天延迟没有被任何校验看见"**：
   9 月月报里 9/30 批次（43 行）**商户订单号为空**，对账 SQL 直接把这些行排除 → 既不拦截也不提示。
4. **真正会出问题的在前面**：10/1~10/11 的资金流水（含 9/30 的 828.01）**已下载到桌面但从未入库**；
   10/1~10/10 的结算日结文件同样未入库。**一旦这些结算文件入库（尤其 10 月月报），
   闸门会把"资金文件缺失"误判成"平台真实缺失"（MISSING_WALLET），中止整个京东经营 ETL**，
   并因依赖关系阻断共享主营收入 ADS 与平台银行汇总。
5. 已落地的 9 月两口径数字**没有算错**（9/30 的到账事件本来就不进收支）；受影响的是：
   ① 对账视图失真；② 10 月经营口径资金侧缺约 65.89 元费用（联盟扣款等）；③ 后续刷新被闸门阻断的风险；
   ④ 10 月结算口径缺 10/1~10/10 共 4,541.29 净额。
6. **修复顺序（关键）**：先补资金（10/8、10/9、10/11 + 回捞 10/10），再补结算（10/1~10/10）——
   顺序反了会在中间某次刷新时触发 MISSING_WALLET 中止。

## 1. 当前两个口径怎么算

### 1.1 结算口径（纯结算，不含资金单）

| 层 | 对象 | 要点 |
|---|---|---|
| ODS | `ods.ods_jd_settlement_raw` | 京东结算单（日结/月报），22 列；`账单日期` 缺失时由文件名推断 |
| 版本去重 | 按 (店铺身份, 单据编号) 取 `ingest_time` 最新版本（京东专属规则，不走 `settlement_source_registry`） | 例：9/28 日报（batch 96）被 9 月月报（batch 153）覆盖；10/13 的 314（空单号）被 377（有单号）覆盖 |
| DWD | `dwd.dwd_jd_settlement_{income,expense,net}_document_detail` | 粒度=单据；三套并行指标 |
| 日期 | `stat_date` = **账单日期**；`event_at` = 费用结算时间（缺失回退账单日期零点） | 与资金单无任何关系 |
| 公式 | 收入=收支方向"收入"的金额；支出=支出方向金额（取负）；净额=收入−支出；`validation_difference_amount` 必须为 0 | 收支方向、符号、币种、应收/应付均强校验 |
| DWS | `dws_jd_settlement_{income,expense}_shop_daily_type`、`..._net_shop_daily` | 按 统计日+店铺+单据类型/费用项 |
| ADS | `ads_settlement_{income,expense,net}_company_shop_daily_type` → 月报视图 `v_settlement_net_company_shop_monthly_metric` | 公司归属在 ADS 层完成 |
| ETL | `etl/jd/run_jd_settlement_metrics_etl.py`（registry key `jd_settlement`，priority 20） | 事务内 TRUNCATE+INSERT，任一校验失败整体回滚 |

### 1.2 经营口径（结算 + 资金混合）

### 1.3 T+1 假设的唯一位置：结算→钱包跨日对账闸门

`run_jd_main_business_finance_etl.py::validate_settlement_to_wallet_reconciliation`（SQL 在本文件内出现 2 份副本，约 481~582 行、598~693 行）：

1. **只检查"最新导入的结算批次"**（`ORDER BY MAX(ingest_time) DESC LIMIT 1`）；
2. **预计到账日**：优先取 `商户订单号` 前 8 位（京东的批次号即"名义到账日"=账单日+1）；无法解析才回退 `MIN(stat_date)+1`（**这就是 T+1 硬编码**）；
3. **无商户订单号的行全部排除**（`NULLIF(merchant_order_no,'') IS NOT NULL`）；
4. **"资金覆盖至" = `MAX(event_at::date)`**——把"有记录的最大日期"当作"连续覆盖"；
5. 状态：`MATCHED` / `PENDING_NOT_YET_ARRIVED`（预计到账日 > 资金覆盖至）/ `MISSING_WALLET` / `AMOUNT_MISMATCH`；
6. **只有 MISSING_WALLET 或 AMOUNT_MISMATCH 会 raise → 整个京东经营 ETL 回滚**。

> 该机制 2026-08-22 引入（commit `c5467a4c`），设计文档 `docs/jd_settlement_wallet_reconciliation.md`。
> 引入目的是修复"把正常 T+1 到账误判成缺失"。本轮国庆暴露的是它的**反向漏洞**（见第 3 节）。

## 3. 闸门在本轮的实际表现与三个盲区

### 3.1 9/30 批次为什么"隐身"

9 月月报（batch 153）中 **账单日期=20260930 的 43 行全部没有商户订单号**（`=""`），
被对账 SQL 的 `NULLIF(...) IS NOT NULL` 条件整批排除：

- 结果：828.01 的 8 天延迟**既没有拦、也没有报**；
- 10/11 运行日志里"结算合计=16,167.79"只包含 29 个批次——9/30 的 828.01 不在其中，正是这个原因。

同样的形态还出现过一次：10/14 09:01 两次运行报 `批次=0`——当时最新批次是 10/13 日报（batch 314，44 行
商户订单号全空），对账**空过**（后续 377 版本带单号才算到）；对比 10/14 20:57/21:02 的运行
（批次=1，先"待到账"后"已匹配"）可见闸门工作正常时应当有输出。

### 3.2 三个盲区（本轮"9 月数据不对"的根因所在）

| # | 盲区 | 后果 |
|---|---|---|
| ① | 只校验**最新导入批次** | 历史批次的迟到/缺失永远不会被复查；9/30 这类月末尾批一旦错过就永久隐身 |
| ② | "资金覆盖至" = `MAX(event_at)`，把最大日期当连续覆盖 | **有空洞时会把"资金文件缺失"误判成"平台真实缺失"（MISSING_WALLET）→ 中止 ETL**；反之，若空洞在最大日期之后，又会把真实缺失当"待到账"静默通过 |
| ③ | 无商户订单号的行整批排除 | 无单号的批次（9/30 月末尾批、部分日报）完全不参与对账，也不计入输出统计 |

### 3.3 若把 10/1~10/10 结算文件直接入库会发生什么（推演）

- 这些日结文件的商户订单号都是**有值的**（如 10/1 文件=20261002…），预计到账日 10/2~10/11；
- 当前 ODS 资金侧 10/1~10/11 **一条记录都没有**，而"资金覆盖至"= 10/15（被 10/12~10/15 的记录顶住）；
- 预计到账日 ≤ 10/15 → 全部判为 **MISSING_WALLET** → `missing_count>0` → **RuntimeError，整个
  `jd_main_business_finance` 回滚**；
- 因依赖关系（`ETL_TASK_PREREQUISITES`），`platform_main_business_income_shared_ads`（七平台共享主营收入 ADS）
  与其下游 `platform_bank_summary` 一并被阻断。
- **注意：即使先补了资金 10/8/10/9/10/11 文件，账单日 10/9 的 99.91 仍会 MISSING_WALLET**
  （它不存在于任何已下载文件），需同时回捞 10/10 的资金流水。
