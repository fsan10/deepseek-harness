# 平台经营收支归属与未映射分类

配置入口为经营收支管理中的“平台收支配置”；查看入口为“全部收支类型”。

| 经营收支归属 | 经营总额 | 全部收支明细 |
| --- | --- | --- |
| 收入 | 正金额增加收入，负金额冲减收入 | 保留 |
| 支出 | 费用扣款增加支出，费用返还冲减支出 | 保留 |
| 不计入 | 不参加经营收入、支出 | 保留来源公式金额和排除原因 |

归属和一级分类独立维护。没有一级分类的已确认收入或支出正常参加总额，一级分类显示“未映射”。清除、停用分类不改变金额；分类下拉不会顺带修改归属。只用于核对或在其他来源已统计的记录不能再次计入。

新业务场景如果没有经营性质认定，显示“归属待确认”；不能仅因原始金额为负就判断为费用。财务确认归属后再进入对应总额。来源字段公式、退款防重和统计日期继续沿用各平台已经验证的口径。

## 数据链路

本次为同一平台资金财务链路增加最终归属DWS阶段：原始ODS → 收入/费用来源DWD → 原来源公式DWS → `dws.dws_<platform>_operating_flow_shop_daily_scene` → 公司店铺DIM → ADS。原来源公式DWS保留用于核对，经营总额读取最终归属DWS。

- 收入指标：`ads.ads_platform_main_business_income_company_shop_daily_category`。
- 支出指标：`ads.ads_platform_expense_company_shop_daily_category`。
- 全部类型明细：`ads.ads_platform_operating_flow_company_shop_daily_scene`，包含不计入和归属待确认项。

纯结算与混合经营收支的来源选择分别验收；结算覆盖来源、资金流水版本、跨店铺隔离和原子刷新见[混合经营收支来源核验说明](operating-finance-source-reconciliation.md)。

- 经营汇总继续读取平台收入、平台支出、独立推广费及银行指标ADS；账户转入广告账户不等于实际广告消耗。

`dim.dim_platform_fee_mapping.operating_treatment`是财务维护的唯一经营归属字段。历史`include_in_platform_expense`及`canonical_operating_treatment`只保留原来源公式阶段的兼容/核对信息，不由新界面修改。`source_component_code`使原本直接在收入SQL中的金额项目也可以在配置页维护。

DataEase已有收入、支出数据集名称不变。新增全部类型明细的数据集使用上述全部类型ADS，日期、公司、店铺、平台筛选器与经营指标联动；可再筛选`operating_treatment`及`mapping_status`。查看全部原公式金额不能将其合计当作经营收入或支出。

## 部署与刷新

下面的命令显式使用项目虚拟环境。命令在进程中读取根目录未提交的`.env`中的PG连接设置，不写入用户或系统环境变量。

```powershell
# 完整迁移及刷新预演，最后回滚所有数据与审计记录
.\.venv\Scripts\python.exe -m etl.platform_finance.run_operating_treatment_migration

# 验收通过后原子提交七平台配置、DWS、ADS及经营汇总
.\.venv\Scripts\python.exe -m etl.platform_finance.run_operating_treatment_migration --apply
```

迁移完成后重启原后台及Worker，再刷新浏览器。新版页面在保存前检查后台能力；旧后台未重启时会拒绝保存，避免旧布尔逻辑改写金额。常规导入和映射刷新任务已接入最终归属DWS阶段。

## 验收约束

- 每个经营金额项目只能分流一次：收入减支出加不计入净额等于原公式净额。
- 总收入等于已分类收入加未映射收入；总支出等于已分类支出加未映射支出。
- 原来源公式、业务键、防重、全部批次店铺归属继续校验；分类缺失本身不阻断刷新。
- 最终DWS与收入、支出ADS双向金额差异必须为零；新增明细不能缺少公司映射。
- 集成测试在事务中回滚全部修改，包括模拟API创建的审计和ETL记录；浏览器预览使用隔离的假数据，不连接登录系统。

养颜轻食2026年9月验收值：主营收入233,496.90元、平台费用5,302.45元；提现165,000.00元和广告账户转账65,210.00元在“不计入”明细中保留。

## 一级分类目录

七平台使用一套业务分类。同一笔费用的扣款和返还使用同一分类，正负方向仍由来源公式决定；销售退款归“销售退款”，退款冻结、临时解冻和已在其他来源计入的核对项归“结算核对”。提现和明确的账户移动归“账户划转”，经营性质尚未确认的项目归“待确认款项”。

2026年10月16日按已存在的业务场景重建后，目录由41项整理为29项：迁移93条配置引用，硬删除18项旧分类，并补充当前业务需要的分类。平台补贴、商品销售收入、售后赔付、小额打款、运费保险、违约金、退货物流费等不再因历史编码不同而出现同名项。名称唯一校验覆盖大小写、空白和已确认的同义名称，例如“退货物流费/退货物流费用”。

分类重建只改变分类编码和名称。`operating_treatment`、来源职责、原公式归属快照、来源符号和防重规则均独立保留；后续正常刷新不会覆盖财务手动选择或清除的分类，也不会重新创建已合并的旧分类。

```powershell
# 重新按当前业务场景整理目录，完成两次七平台刷新和每日金额回归后回滚
.\.venv\Scripts\python.exe -m etl.platform_finance.rebuild_operating_categories --output <分类预演.json>

# 所有校验通过后原子提交目录、配置及看板ADS
.\.venv\Scripts\python.exe -m etl.platform_finance.rebuild_operating_categories --apply --output <分类验收.json>
```

该命令是明确重建业务分类时使用的迁移工具，日常导入无需执行。金额回归基准是重建前已发布的每日ADS，不能替代独立财务对账。新经营场景沿用已确认来源性质；尚无性质认定的场景保留明细等待确认。

## 快手资金与结算的主辅关系

快手混合经营指标以结算单为主、资金单补充。结算单提供商品收入、结算退款和平台费用；资金单补充结算后退款、独立费用及原费用返还。货款结算到账作为核对项，不重复作为商品收入。数据按结算时间或资金入账时间分别归日。

客户退款以负数冲减收入，费用表不再计算这笔客户退款。佣金、技术服务费等返还则以负数冲减相应费用。费用ADS采用正数表示费用、负数表示费用返还；若看板将费用展示为负数，应在展示层保持一致，不能因此再改动计算金额。

禧饮2026年9月已确认收入133,806.50元、费用61,377.73元：收入136,217.40－结算退款1,758.02－资金退款652.88；费用61,032.08＋资金补充费用净额345.65。资金退款已在收入侧使用一次，不再冲减费用。8月陌时财务基准与系统现值的差异已拆出；用户确认本轮暂不继续判断，保留系统现有口径和金额，不能将此标为独立财务对账通过。

## 经营归属与来源用途（第二版）

财务在“平台收支配置”维护收入、支出、不计入；未知性质显示“归属待确认”。一级分类可以先分配或清除，归属待确认不再阻断分类操作。已确认的收入/费用即使分类未映射也保留金额；停用分类不会排除经营金额。

来源用途在“来源依据”中单独显示：

- **可配置的独立金额**：经营归属由财务决定。旧`RECONCILIATION`角色和旧`canonical_operating_treatment='excluded'`快照不会锁死它。视频号“极速退款垫资／回补极速退款垫资”属于此类，迁移保留原“不计入”设置，之后可按业务需要修改。
- **已由主来源统计／重复业务事实**：按明确的来源合同排除并显示中文依据。例如资金净到账不能再当作已由结算单还原的商品收入，结算退款过程不能重复进入经营退款。原生流水版本、文件覆盖、批次店铺和既有退款防重继续执行。

点击“来源依据”可以查看判断理由、当前归属和规则建议，以及支持核对的关联批次、来源行及订单身份。未证实的错误标签在具有可核对身份且没有已统计关联时，可以填写独立业务依据并更正。已经确认的来源合同不能仅因为当前缺少主来源就解除；需要先核实来源身份或更正描述匹配，避免后续主来源补齐时双计。更正不会删除ODS。

新增类型统一通过已确认场景规则给出建议；没有可靠规则的项目保留待确认，不凭金额正负、工作表名称或一级分类推断。小红书新增“其他服务款”不再一律默认为费用，新增订单交易类型保留公式金额等待确认，不再仅因名称未知使整个平台无法刷新。数据字段、金额解析、来源身份等真正的完整性错误仍停止刷新。

修改经营归属前，页面展示涉及的店铺、月份、来源数量和收入/费用变化；规则通常影响全部匹配的历史数据。未处理的新来源尚无已发布金额时，预览会说明需要重算后体现。收入和费用沿用来源公式符号：客户退款归收入时仍为负，费用返还归支出时为负费用。

保存只代表配置已写入。配置行显示等待重算、重算中、已生效或失败，并能打开ETL详情；后台读取最终经营DWS后刷新收入、费用及全部类型ADS，DataEase再查询对应ADS。失败的归属修改记录拒绝原因，便于追溯。

同一业务的原始名称和公式组成项保留别名关联，只显示有效配置入口。例如小红书“申诉调账”合并到实际控制金额的收入组成项入口，避免两个开关互相误导。

```powershell
# 读取项目根目录.env，只在当前进程使用PG设置。
# 两次七平台刷新，验证每日/月份金额和现有财务设置不变，默认最后回滚。
.\.venv\Scripts\python.exe -m etl.platform_finance.run_operating_policy_migration --output <规则预演.json>

# 所有回归通过后原子提交；不自动改变垫资等项目的现有经营归属。
.\.venv\Scripts\python.exe -m etl.platform_finance.run_operating_policy_migration --apply --output <规则验收.json>
```

迁移只将来源用途与经营选择分开，保留原平台公式和日期。迁移后重启后台和Worker并刷新浏览器；第二版前端会拒绝向旧后台保存。数据库事务集成测试覆盖垫资往返切换、待确认分类、来源纠错及重复来源保护，全部回滚；浏览器验收使用无登录、无数据库的隔离样例服务，结束后关闭。

## 可维护的场景清洗规则

“经营收支管理 → 收支场景清洗规则”是独立列表页面，也可从平台收支配置跳转；支持平台、来源、启用状态和关键字筛选。规则按平台、资金/结算来源及可选业务类型维护PostgreSQL正则。规则按执行顺序从小到大逐条全局替换，替换内容留空表示删除，支持捕获组引用。规则可以新增、编辑、停用和重新启用；停用后通过来源重算恢复相应名称。

同一套规则用于ODS候选页面、费用DWD场景名称、统一场景匹配以及最终经营DWS展示。原始业务描述、订单号、流水号及ODS不修改。新增导入与历史重算均遵循当前规则；不按清洗后的名称删除或去重原生流水。

快手初始规则删除订单号/退款单号标签及其值，清除“退款-快手电商-订单编号”中的渠道与单号尾缀；团长返还清除用户指定的“-cps团长三方分佣户-退款单号”尾缀。平台服务费、推广者与MCN等有业务区别的信息保留，避免不同分类被误合并。只有限定平台及来源的规则生效，不将快手模板套用到其他平台。

全平台检查同时将京东已识别的结算后退款固定文案简化为“结算后售后退款”，并为天猫保证金管控及百补佣金清除逐笔订单标签、付款方和邮箱信息。原始单号和备注继续保存。同一性质的多个旧收入组成项可以共用一个配置入口，各组成项仍按原编码只计算一次。

保存前必须预览当前来源、配置和发布样本，也可以补充尚未导入的场景。预览显示原始/清洗后名称、名称数量及冲突；清洗结果为空、超长、重复执行继续变动、正则无效/超时或不同分类/归属/来源职责被合并时禁止保存。预览不写入规则、任务或审计；规则或来源变化后需重新预览。未来尚未出现的业务描述不能由当前样本完全覆盖，刷新仍执行字段、场景、身份和金额校验。

同名且来源计算语义与财务配置相同的历史规则只展示一个配置入口，修改归属、清除或停用分类同步作用于该组；原映射和来源明细保留。规则修改记录操作审计并创建受影响平台的异步ETL任务。

“全部收支类型”保留日期与店铺粒度，条数是日汇总记录数，并单列不同收支场景数，不将日记录数称为类型数。“不计入原因”展示在经营归属右侧；映射状态单独展示。配置表隐藏内部编码与重复业务类型列，来源用途详情集中在“来源依据”，主列表只保留映射和重算状态。历史自动备注中的未映射/待确认状态按当前确认配置更新，不覆盖具体财务业务说明。

全部类型页面按显示的日期、店铺、来源、场景、分类和经营归属汇总。同一业务的不同内部公式编码不再拆成重复可见行；金额和组成数量求和，ADS中原公式身份仍保留。不计入原因不同的记录仍分别展示，便于核对。

```powershell
# 两次七平台刷新，比较每日/公司/店铺/来源/分类/归属金额及组成明细数。
# 名称与场景编码允许因合并变化，金额、分类和来源事实必须不变。
.\.venv\Scripts\python.exe -m etl.platform_finance.run_scene_normalization_migration --output <场景预演.json>
.\.venv\Scripts\python.exe -m etl.platform_finance.run_scene_normalization_migration --apply --output <场景验收.json>
```

该迁移默认先核对当前DWD与ODS的21项原生来源身份，再只更新场景名称、受影响的费用公式汇总以及七平台最终经营DWS/ADS。比较14张来源DWD去除名称和刷新时间后的内容指纹，确保金额、日期、状态和原始身份字段不变；金额与来源组成数量逐日回归，两次刷新验证幂等。需要同时从ODS重建全部来源时增加`--rebuild-sources`；正常导入和日常完整ETL仍使用原有全链路。旧的未映射检查也使用同一清洗匹配键，防止将已匹配费用误报为未映射。

系统生成的财务说明会随经营归属和一级分类更新，清除分类时同步说明为未映射；已手动改写的具体业务说明保留。
