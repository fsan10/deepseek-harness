# Automation 网页 Run 断点恢复与人工处理 V1

适用分支：`codex/automation-component-workbench`。此方案复用 `scripts/auto_download`
现有 JSON 检查点、Cloak Login CDP Profile、飞书 Challenge 与
`ops.automation_run`；**不改变 Codex 定时脚本、工作日/节假日策略以及报表校验规则**。

## 1. 两种继续方式

| 当前 Run 状态 | 操作 | 行为 |
| --- | --- | --- |
| `failed` | 修复脚本/环境后「修复后继续」 | **同一个 Run ID**重新排队，已成功的报表步骤按该 Run 的独立 JSON 检查点跳过；新尝试和原失败尝试都保存在执行详情。 |
| `needs_human` | 人工完成后「继续任务」 | 同一个 Run ID 恢复到 `queued`；若该 Run 的最新飞书 Challenge 已被回复，Worker 也会自动恢复。 |
| `running` 且正在等待验证码 | 工作台「等待人工处理」实时出现该组件 | 仍在本次运行中，**不要**重复点继续。 |
| `failed` / `success_with_warnings` 且不再需要操作 | 填原因「忽略提醒」 | **只隐藏“需要关注”提醒**，执行结果、报错、组件事件都不修改；故障中心/执行记录仍保留历史。 |
| `cancelled` | 新建任务或重试 | 主动取消后不能在原 Run 上隐式续跑。 |

下载 Run 的检查点现独立保存在
`<log_directory>/checkpoints/automation_run_<run_id>.json`。
旧日期检查点只会导入数据库证明确属**同一个 Run**的成功步骤；
找不到/无法验证历史检查点时，为防重复创建平台导出任务，会明确拒绝盲目重放。

暂停/失败的交互式 Run 会保留自己的 `automation_resource_lock`，状态标记为
`paused`（资源中心显示“保留现场”），**不继续占用 Worker**。
同一 Run 恢复时可重新领取自己的预约；新 Retry Run 可以继承预约。
在“需要关注”里填写原因“忽略提醒”会主动释放失败 Run 的预约；
`needs_human` 必须继续或取消才能释放，不允许只隐藏。
这保证同一 `resource_key` 的工作台任务不会在人工离开期间破坏现场。
**边界：当前系统下载任务使用 job 级资源键，多条不同 lane 的下载任务或不经
Automation 的外部 Codex/手工脚本尚未纳入跨工具统一 Profile 锁；若同时
操作相同 Profile，仍需通过运维安排隔离。**

原 Run 的 `started_at` 保留首次领取时间，同时新增
`attempt_started_at` 记录**最近一次领取时间**；恢复后的 30 分钟超时判断
只看当前这次领取，不会拿昨天的时间误判刚恢复的任务已卡死。

完整的失败尝试记录留在「执行详情」，「每日成果」及首页业务进度按
Run、Profile、模块和步骤显示最新尝试，不将恢复前的错误当成最终成果。

## 2. 长时间验证码等待

首先检查工作台「等待人工处理」里的平台、店铺、Profile、Challenge 状态。
若 Worker 仍在轮询，直接在飞书回复；若进程已退出，Run 进入
`needs_human`，点击「继续任务」。

继续时，总控优先附着到**仍在运行的 Cloak Profile**；只有实例已关闭才
重新启动同一个持久化 Profile。抖音/快手订单验证码和京东订单文件提取码
采用各自的平台脚本状态文件：

- 尚有效的 Challenge：继续等待原 ID，不重复触发短信/文件密码；
- 已过期/取消：清理旧 ID，重新触发平台的“获取验证码”或“获取/重新发送密码”后，创建**新的**飞书 Challenge；
- 转发服务临时超时/断线：保留原 ID，避免重复发送；之后可以继续。

抖音已下载的加密 ZIP 恢复解压节点时，仍有效且已接收的密码直接使用；未收到的原请求重新向群发送人工提醒，
并保留原截止时间。请求过期则创建新的 5 分钟人工等待，请回复原 ZIP 对应的密码；不重新下载 ZIP，也不等待平台再次发送密码。
自动接收成功与人工回复成功都发送不含代码的群回执，便于确认接收链路是否工作。

需要扫码或手工滑块等**没有机器可获取的结构化 Challenge**，仍须由负责人
操作后手动点击「继续」；若目标平台不再保留当前页面/登录态，脚本会按其
现有恢复入口重新导航，不保证任意 Python 指令级续执行。

## 3. Flow Studio 范围

正式 Flow 始终按该 Run 保存的不可变 `flow_version_id` 执行；
修复 Handler 实现后，可以在同一 Run 再次执行失败节点。安全检查点只对
*可验证文件仍存在*的文件/归档步骤和*已确认成功*的 ODS/ETL 下游副作用
跳过。浏览器连接、登录、页面导航、验证码等需在新 Worker 进程中重建上下文，
**不直接序列化 Page、Cookie、Token 或明文验证码**。

如果变更的是 Flow 节点定义而非 Handler 代码，旧 Run 的定义不会偷偷升级，
应发布新的 Flow Version 并在新 Run 中验证。

## 4. 部署与人工回归检查

先在**测试环境**备份数据库和现有 `.automation_logs/checkpoints`，
执行项目 Automation SQL 迁移，再重新启动 server 和独立 Worker。
旧 `ops.automation_run` 会自动补充告警确认和 `attempt_started_at` 字段，
资源锁表会增加 `lock_state`；部署前请让旧 Worker 正常退出并备份数据库。
更新前已经失败/暂停、却未保存资源锁的旧 Run，不保证能追溯并锁住其历史现场。

建议用测试店铺按顺序验收：

1. 制造第 2 个报表步骤失败，第 1 步已保存检查点；修复后按「修复后继续」。
   核对 Run ID 不变、成功步骤不重复提交、原失败记录仍可查看、最终状态为成功。
2. 制造飞书验证码长时间未回复：还在运行时首页立刻显示人工任务；
   超时变为 `needs_human` 后 Profile 不被自动关闭；数小时后「继续」，
   验证旧 Challenge 过期时**平台确实重新发送验证码**、飞书出现新的 Challenge。
3. 同一天启动另一个测试 Run；核对不同 Run 的 JSON 检查点不串号。
4. 制造失败后「忽略提醒」，填写原因；首页告警消失，
   故障中心与执行详情仍可按原失败状态检索。
5. 用 Retry 链（A 失败 → B 失败 → C 成功）验证 A/B 历史提醒均自动标记已处理。
6. 验证成功后的「每日成果」不因历史失败/恢复尝试被重复计算。

> Step 数为 0）；需要仓库 Actions 环境恢复后再进行 CI 验证。
